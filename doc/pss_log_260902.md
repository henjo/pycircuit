

### 2026-09-27 — refactor phase 4: the transient's PCNR copies, and the batched JAX TLine

**1. One PCNR iteration** (bit-identical).  The LMM step and an implicit
Runge-Kutta stage ran the same PCNR loop: predict, refine, the junction
test and the step test.  They differ only in the augmented system:
the multistep companion, or the stage's effective one.  The loop is now
`_pcnr_newton(x, v_lim, junctions, assemble, msg, t)`, and each caller
keeps its after-convergence work (the LMM its Schur Jacobian and branch
check, the stage its `limit(x, x)` sync).  The success/fallback
bookkeeping, in three copies, is `_pcnr_attempt(solve, on_fail, catch)`.
The LMM path's catch stays `Exception`: narrowing it to a non-convergence,
as the stage paths catch, is a behaviour change of its own.
- A suspected latent defect was checked and CLEARED.  The coupled step
  imports `NoConvergenceError` locally, which makes the name local to the
  whole function, so an `except` before the import would have been an
  UnboundLocalError.  But the function's FIRST statement imports it.
- The full gate matched the previous one call for call.  The PCNR subset
  (266 tests) recorded counters and status identical.

**2. `JAXTransient.solve_batched` started a TLine from zero.**  `solve`
fills each line's delay history with its DC state from `x0`.  The batched
copy of that setup left it at zero ("Init with zero for now"), so the
delayed terms read 0 V for the first TD.  Measured on a matched 1 V line
started from its operating point: `solve` held v(b) at exactly 0.5 V,
while `solve_batched` was 0.5 V off at the first point.  Nor did it check
the ring buffer's overflow, which `solve` raises on.
- One `_tline_setup(x0s)` serves both entry points, each lane from its
  own state.  `solve`'s history is built by the same operations as before.
- The batched loop counts accepted steps per lane and raises as `solve`
  does.
- Tests:
  - `test_solve_batched_starts_a_tline_from_each_lanes_operating_point`:
    two lanes at different loads, 0.5 and 0.75 V held.
  - `test_the_tline_ring_buffer_overflow_raises_on_both_entry_points`:
    the depth is shrunk to 16; the traced code reads it at trace time.
  - Both fail on the old code: 0.5 V off, and DID NOT RAISE.
- ⚠ A tool lesson from it.  The first ruff check compared the SUMMARY
  lines of the old and new trees ("2 hidden fixes" both), and so hid a new
  F821 (the `tlines` list the setup still needed) behind an equal count.
  Compare the findings, not their count.
