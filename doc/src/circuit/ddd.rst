=================================================================
Determinant Decision Diagrams (DDD) for symbolic circuit analysis
=================================================================

.. note::

   **Work in progress.** This page is written *alongside* the implementation,
   one section per stage (see ``doc/ddd_plan.md``). Every table and figure below
   is generated by running the real code when the documentation is built, so it
   cannot drift from what is actually implemented — if the code changes
   incompatibly, this page changes with it or the build fails.

   Implemented so far: the measurement harness (Stage B) and the layered
   determinant construction with Cramer solving (Stage P0). The s-expanded
   multiroot form is next.

Why this exists
===============

A fully symbolic network function is a ratio of determinants, and a symbolic
determinant of an ``n x n`` matrix has up to ``n!`` product terms. Expanding it
is hopeless beyond trivial circuits — but the terms share an enormous amount of
structure, and a *Determinant Decision Diagram* is a graph that represents the
expansion with that sharing made explicit: a huge number of product terms, a
modest number of vertices.

Whether that pays off for pycircuit is an empirical question, not an assumption.
pycircuit already has representations that avoid the blow-up — notably the
sequence-of-expressions solver (:doc:`soe_symbolic`) — so the bar for adding
another one is that it must beat what we already have, on our own circuits. That
is why the measurement harness comes first.

How the diagram is built
========================

Expand a determinant along a row and you get one term per nonzero entry, each
multiplying the determinant of the *minor* left behind::

    det(M) = sum_j  (-1)^(p+q) * M[i,j] * det(M without row i, column j)

A DDD is that expansion written as a graph. Each vertex stands for one
``(entry, minor)`` pair and has two outgoing edges:

* a **1-edge** (solid) into the minor left after deleting the entry's row and
  column — "take this term";
* a **0-edge** (dashed) to the next entry of the same expansion — "skip it".

Reading a vertex as ``sign * entry * value(1-edge) + value(0-edge)``, every path
from the root to the ``1`` terminal spells out one product term of the
determinant. Evaluation costs one multiply and one add per vertex — and no
division, so unlike an elimination-based solver there is no pivot that can vanish
for particular component values.

Here is the whole diagram for a general 3×3 matrix, generated by building one:

.. exec-rst::

    import sympy
    from pycircuit.circuit.ddd import ddd_of_matrix

    A = sympy.Matrix(3, 3, lambda i, j: sympy.Symbol('a%d%d' % (i, j)))
    D = ddd_of_matrix(A, order='row')

    print(".. graphviz::")
    print("")
    for line in D.to_dot(name='ddd3').splitlines():
        print("   " + line)
    print("")
    print("The 3×3 determinant has %d product terms, held in %d vertices."
          % (6, D.size))

Sharing is the whole point
==========================

Nothing above would help if each minor were expanded afresh every time it was
reached — the graph would just be the ``n!`` expansion drawn differently. What
makes it compact is that minors are **memoised on their (row indices, column
indices)**, so a minor reached along several paths is expanded once and pointed
at from everywhere. That dict *is* the sharing mechanism; no BDD package is
involved.

There is an exact way to check it works. Shi (TCAS-II 2010) proves that for a
**full** ``n×n`` matrix expanded row-wise, the optimal diagram has exactly
``n·2^(n-1)`` vertices. The table below builds one and compares:

.. exec-rst::

    import sympy
    from math import factorial
    from pycircuit.circuit.ddd import ddd_of_matrix

    print(".. list-table:: Full n×n matrix — measured size vs the proven optimum")
    print("   :header-rows: 1")
    print("   :widths: 6 16 16 18 12")
    print("")
    print("   * - n")
    print("     - product terms")
    print("     - ``|DDD|`` measured")
    print("     - n·2^(n-1) optimum")
    print("     - matches")
    for n in range(1, 8):
        A = sympy.Matrix(n, n, lambda i, j: sympy.Symbol('a%d%d' % (i, j)))
        D = ddd_of_matrix(A, order='row')
        opt = n * 2 ** (n - 1)
        print("   * - %d" % n)
        print("     - %d" % factorial(n))
        print("     - %d" % D.size)
        print("     - %d" % opt)
        print("     - %s" % (D.size == opt))

This is the single most valuable test in the suite, because a diagram whose
memo table never hits is still perfectly *correct* — just exponentially large.
Correctness tests cannot detect broken sharing; this identity can.

Note also what the identity says about the general case: ``n·2^(n-1)`` is still
exponential. A DDD does **not** make a dense determinant tractable. Its value
comes entirely from *sparsity* — which is why the circuit measurements below
matter more than any of this.

Signs, and where they come from
===============================

The cofactor sign ``(-1)^(p+q)`` uses the entry's position *within the current
minor*, not in the original matrix, and it is fixed as the vertex is created —
the layered construction needs no separate sign pass over the finished graph.

That convenience has a cost worth knowing about: a sign error would be a
construction bug with no separate stage to inspect. It is caught by evaluating
the diagram numerically against ``numpy``'s determinant on random sparse
matrices, which is exactly what ``test_signs_against_numeric_determinant`` does —
a wrong sign changes the value while leaving every structural property intact.

Expansion ordering
==================

Which row or column to expand next is chosen **on the fly**, so there is no
symbol-ordering pre-pass. ``min-degree`` (the default) takes whichever row or
column has fewest nonzeros; ``row`` always takes the first row, which is what
makes the identity above hold exactly.

Ordering changes the graph but never the value. On a sparse circuit matrix it
changes the *size*, which is where it matters:

.. exec-rst::

    from pycircuit.circuit import benchmark_circuits as bc
    from pycircuit.circuit.ddd import ddd_of_matrix

    print(".. list-table:: Expansion ordering on a fully symbolic RC ladder")
    print("   :header-rows: 1")
    print("   :widths: 10 10 16 16")
    print("")
    print("   * - N")
    print("     - dim")
    print("     - ``|DDD|`` row-wise")
    print("     - ``|DDD|`` min-degree")
    for N in (4, 8, 12, 16):
        A = bc.rc_ladder(N).A
        print("   * - %d" % N)
        print("     - %d" % A.rows)
        print("     - %d" % ddd_of_matrix(A, order='row').size)
        print("     - %d" % ddd_of_matrix(A, order='min-degree').size)

On a real circuit
=================

The same construction, applied to a two-section RC ladder built the ordinary way
with :class:`~pycircuit.circuit.SubCircuit` and stamped through the normal MNA
path — the matrix an :class:`~pycircuit.circuit.analysis_ss.AC` analysis would
hand any other backend:

.. exec-rst::

    from pycircuit.circuit import benchmark_circuits as bc
    from pycircuit.circuit.ddd import ddd_of_matrix

    system = bc.rc_ladder(2)
    D = ddd_of_matrix(system.A)

    print(".. graphviz::")
    print("")
    for line in D.to_dot(name='ladder2').splitlines():
        print("   " + line)
    print("")
    print("Matrix is %d×%d; the diagram has %d vertices over %d distinct minors."
          % (system.dim, system.dim, D.size, D.n_minors))

Vertex labels are matrix positions ``aij``; a leading minus is the cofactor sign.
Every diagram on this page is rendered from a diagram the code actually built —
``to_dot()`` requires a vertex limit and refuses anything larger, so a real
circuit's thousands of vertices can never reach Graphviz.

How we measure
==============

The comparison set is **fixed in advance**, in
:mod:`pycircuit.circuit.benchmark_circuits`, so that it cannot be chosen after
seeing results. Every circuit in it is an ordinary
:class:`~pycircuit.circuit.SubCircuit` stamped through the normal MNA path — the
matrix a backend is measured on is the matrix an analysis would hand it, never a
hand-written one.

Metrics, and why each is separate:

``size``
    Representation size in the backend's own unit: ``count_ops`` for expression
    backends, vertex count for graph backends.

``payload``
    The total operation count of what each unit *carries*. Reported beside
    ``size`` because the units are **not** interchangeable — a backend whose
    vertices each hold a whole matrix entry has fewer, fatter units than one
    counting component-level operations, and would otherwise look artificially
    compact.

``build_s`` vs ``eval_s``
    Construction time and per-point evaluation time, always reported
    **separately**. Conflating them is not a hypothetical mistake: an earlier
    backend was adopted here on a "~10x faster" figure that turned out to be
    timing numeric evaluation rather than the symbolic extraction that was
    actually needed.

``peak_rss_kb``
    Peak memory of the run. A graph vertex is cheap in C++ and much less so as a
    Python object, and memory — not time — is the likely first casualty of a poor
    expansion ordering.

``status``
    ``ok`` / ``timeout`` / ``killed`` / ``error``. Several symbolic backends do
    not fail, they *hang*; "did not finish within T" is a first-class result, so
    every case runs in a subprocess under a wall-clock timeout and an
    address-space cap.

Harness self-check
==================

Before the harness can referee anyone else's numbers it has to reproduce our
own. The published sequence-of-expressions table (:doc:`soe_symbolic`) reports
73/157/241/325 operations for the hand-built ladder at ``N`` = 4/8/12/16. This
runs the harness against those figures at build time:

.. exec-rst::

    from symbolic_bench import measure

    expected = {4: 73, 8: 157, 12: 241, 16: 325}

    print(".. list-table:: Harness validation — SoE op counts reproduced")
    print("   :header-rows: 1")
    print("   :widths: 8 16 16 12")
    print("")
    print("   * - N")
    print("     - measured")
    print("     - published")
    print("     - matches")
    for N in sorted(expected):
        rec = measure('legacy_soe:%d' % N, 'soe')
        print("   * - %d" % N)
        print("     - %s" % rec.get('size'))
        print("     - %d" % expected[N])
        print("     - %s" % (rec.get('size') == expected[N]))

Baselines
=========

The current backends on the fixed circuit set, measured at build time. These are
the numbers a DDD implementation has to beat — recorded *before* any DDD code
exists, so the comparison is not retrospective.

``rc_ladder_N`` is a fully symbolic ``N``-section RC ladder (every component a
distinct symbol); ``semi`` keeps only two resistors symbolic; ``mfb`` is the
multiple-feedback filter of :doc:`examples/example10`, which contains a
:class:`~pycircuit.circuit.Nullor` and so has a structurally different sparsity
pattern.

.. exec-rst::

    from symbolic_bench import measure

    specs = ['rc_ladder:4', 'rc_ladder:8', 'semi:8', 'mfb']
    backends = ['symbolic_poly', 'soe', 'ddd']

    print(".. list-table:: Backend baselines (generated at build time)")
    print("   :header-rows: 1")
    print("   :widths: 20 16 8 10 12 12 10")
    print("")
    print("   * - circuit")
    print("     - backend")
    print("     - dim")
    print("     - size")
    print("     - build (s)")
    print("     - eval (s)")
    print("     - correct")
    for spec in specs:
        for b in backends:
            rec = measure(spec, b)
            if rec.get('status') != 'ok':
                print("   * - %s" % spec)
                print("     - %s" % b)
                print("     - -")
                print("     - %s" % rec.get('status'))
                print("     - -")
                print("     - -")
                print("     - -")
                continue
            print("   * - %s" % spec)
            print("     - %s" % b)
            print("     - %s" % rec.get('dim'))
            print("     - %s" % rec.get('size'))
            print("     - %.3g" % rec.get('build_s', 0.0))
            print("     - %.3g" % rec.get('eval_s', 0.0))
            print("     - %s" % rec.get('correct'))

Reading the table: ``size`` for ``symbolic_poly`` counts operations in the
expanded ``N(s)/D(s)``, which is why it grows sharply with ladder length; the SoE
keeps a shared assignment list and grows linearly; the DDD counts vertices in the
two numerator diagrams a transfer function needs (the shared determinant cancels
in the ratio ``x_out/x_in``, so it is not part of that query's cost).

Because those units are not identical, ``payload`` is the fairer comparison for
the DDD — it counts the operations inside the matrix entries each vertex carries.
Even on that measure the diagram is the smaller representation here.

.. note::

   **A robustness difference the harness turned up.** Building this comparison
   exposed a limitation worth recording before DDD is measured against it: the
   sequence-of-expressions solver performs Gaussian elimination **without
   pivoting**, so a pivot that is nonzero *symbolically* can still evaluate to
   exactly zero at particular parameter values, yielding ``NaN``. The first
   dense fixtures here hit that by accident, because a regular arithmetic value
   pattern is unusually good at producing a singular leading minor; they now use
   seeded, diagonally-dominant values instead.

   This matters for the comparison because **DDD evaluation is division-free** —
   each vertex contributes only ``D0 + sign * entry * D1``, one add and one
   multiply — so it has no pivots to vanish. That is a genuine robustness
   advantage over any elimination-based representation, independent of size, and
   it should be weighed alongside the operation counts rather than lost in them.

Running it yourself
===================

.. code-block:: console

    $ python benchmarks/symbolic_bench.py --validate      # harness self-check
    $ python benchmarks/symbolic_bench.py                 # whole suite
    $ python benchmarks/symbolic_bench.py -s rc_ladder:8 -b soe

Each case runs isolated, so a backend that exhausts memory takes down only its
own child process.
